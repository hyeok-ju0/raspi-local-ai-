# AI/소프트웨어 계층 재설계 기록 (2026-08-25 ~ 08-28)

중간발표 피드백("기성품 조합에 불과함", "모델 선정 이유 불명확") 대응으로 진행한
AI/소프트웨어 계층 재정립 전체 과정. 하드웨어는 변경 없음, 소프트웨어 계층만 대상.

---

## 1. 정체성 재정립

### 배경
중간발표에서 두 가지 지적을 받음:
- 소프트웨어 스택(Ollama, Open WebUI, Tailscale 등)이 노트북에서도 동일하게 실행 가능한
  범용 조합이라는 지적 — AI 스택 계층에 정확히 해당, 하드웨어 결합 요소(전원 감지,
  킬 스위치 등)는 해당 없음
- 모델 선정 이유가 목적-모델 매핑 근거 없이 성능 실측 중심으로만 기록되어 있었다는 지적

### 결정된 정체성
- **AI 역할**: 범용 채팅형 비서 단일 역할 (Claude류의 대화 품질 지향)
- **감시자(프라이버시 워치독) 기능은 폐기함** — 아래 "폐기된 설계: 감시자 기능" 참고
- 휴대 모드: 빠른 질의응답·검색 대체, 메모/아이디어 정리
- 거치 모드: 휴대 모드 기능 + 복잡한 추론/분석
- "로컬 AI가 기기의 핵심 인터페이스"라는 기존 정체성은 유지, 보안(킬 스위치 등)은
  AI가 아닌 별도 소프트웨어 기능들이 담당

### 폐기된 설계: 감시자 기능
초기에는 "AI가 대화 중 민감정보 입력을 감지하고 경고"하는 시스템 프롬프트 수준의
감시자 역할을 계획했으나, 논의 끝에 완전히 폐기함. 이유:

1. 로컬 AI의 핵심 가치("외부로 전송 안 되니 민감정보를 자유롭게 입력해도 된다")와
   감시자 경고("민감정보 입력하면 안 됨")가 논리적으로 충돌함
2. 실제 위협(로그 평문 저장, RAG 인덱스 잔존, 화면 노출, 클립보드 잔존)은 전부
   아래 "채택된 비-AI 보안 기능"으로 이미 커버됨 — AI 감시자가 추가로 막아주는
   부분이 실질적으로 없음
3. "AI가 스스로 취약점을 찾아 임시 차단"하는 더 야심찬 버전도 검토했으나,
   LLM은 시스템에 대한 읽기/쓰기 권한이 없으면 이 자체가 물리적으로 불가능하고,
   도구 권한을 주는 방식은 Pi5급 소형 모델의 신뢰도 문제 + 자율 시스템 조작의
   보안 위험 때문에 기각

### 기능 (3개, 채택)

- 로컬 일정 관리 (radicale 등)

## 3. 모델 재선정

### 1차 선정 (실측 전, 문서 스펙 기준) — 이후 실패로 판명
- 휴대: Gemma 4 E2B, 거치: Qwen3 8B
- 선정 기준 우선순위: 긴 컨텍스트/RAG 적합성 > 메모리·속도·시스템프롬프트 순응도(공동) > 한국어
- 근거: 두 모델 모두 128K 컨텍스트, Gemma4는 시스템 롤 네이티브 지원

### 실측에서 드러난 문제
- Gemma 4 E2B가 반복적으로 OOM(메모리 부족)으로 강제 종료됨, 심할 때는 Pi5 전체가
  멈췄다가 재부팅되는 사태까지 발생 (파일시스템 손상은 없었음, 매번 정상 복구됨)
- 원인 조사 결과 **Gemma 4 E2B는 "E2B"(유효 파라미터 약 2B)라는 이름과 달리, 실제
  총 파라미터는 5.1B이며 vision/audio/tools/thinking capability를 전부 포함**하고
  있어, 텍스트 전용으로만 써도 멀티모달 인코더용 메모리를 상시 점유함
- num_ctx를 32768 → 16384로 낮춰도 OOM 시점의 실제 메모리 사용량(anon-rss)이
  거의 줄지 않음 → 컨텍스트 캐시가 아니라 모델 자체(가중치+멀티모달 버퍼)가
  문제의 핵심이었음
- 반면 Qwen3 8B(8.2B, 텍스트 전용, vision/audio 없음)는 파라미터가 더 큰데도
  안정적으로 실행됨 — vision/audio 유무가 결정적 차이였음

### 환경 요인 (최종적으로 결정적이었던 원인)
- Pi5에 Nextcloud+Redis+MariaDB 스택(다른 사이드 프로젝트용)이 상시 구동 중이었고,
  이게 지금까지 AI 모델 메모리 계산에 전혀 반영되지 않고 있었음 → 현재 해당
  사이드 프로젝트 일시 중지, 스택 정지 조치함
- **결정적 원인**: Pi5 자체 화면에서 "일반 데스크톱 Chromium 브라우저로 Claude와
  대화하며 동시에 Pi5에서 AI 모델을 테스트"하는 방식으로 작업해왔음. 이게 실제
  킥오스크 배포 환경(Open WebUI 풀스크린 전용, 다른 탭 없음)과는 전혀 다른,
  훨씬 무거운 조건이었음. Chromium 완전 종료 후 재테스트하니 Gemma 4 E2B도
  정상 구동됨(여유 300MB 이상 유지) → **모델 자체보다 테스트 환경이 더 큰 문제였음**
- 다만 킥오스크 조건에서도 Open WebUI를 노트북(Tailscale)으로 원격 접속해
  테스트한 결과 Gemma 4 E2B는 여유 27MB까지 떨어짐 → 위험 수준으로 판단,
  **모델 재선정 재추진 확정**

### 2차 선정 (재추진) — 진행 중
- **1순위: Qwen3 4B** (텍스트 전용, 128K 컨텍스트 유지, Qwen3 8B와 같은 생태계라
  chat template 문제 재발 가능성 낮음)
- 실측 결과: 정상 구동, 여유 메모리 300MB 이상 안정적으로 유지됨 (Chromium 없는
  조건 기준)
- 대안 후보(우선순위순): Qwen3 1.7B(컨텍스트 32K로 제한, RAG 우선순위와 충돌),
  Qwen3 0.6B(동일 제약), SmolLM2 1.7B(실측 메모리 사용량이 오히려 큰 사례 보고됨),
  BitNet B1.58 2B 4T(생태계 미검증), Gemma 3 4B(구형, 생태계 검증은 더 됐으나
  Gemma 계열 템플릿 문제 재발 가능성 배제 못 함)
- 미해결: Qwen3 4B의 thinking 모드가 기본 켜짐 상태로 나옴. Ollama Modelfile에
  `PARAMETER think false`는 지원되지 않는 파라미터(공식 미지원, 요청만 있는 상태).
  CLI `--think=false`도 버그 리포트 다수. **Open WebUI 관리자 패널의 모델별
  Advanced Params에 think 관련 토글이 있는지 확인 필요** (아직 미확인)

## 4. RAG 설계

| 항목 | 결정 |
|---|---|
| 임베딩 모델 | nomic-embed-text-v2 (v1 대비 다국어/한국어 강화, 같은 계열이라 마이그레이션 쉬움) |
| 저장소 | Open WebUI Knowledge Base — 수업자료 KB / 개인노트 KB 분리 |
| KB 공유 | 휴대/거치 모드 동일 KB 공유 |
| 동기화 | Open WebUI 내장 `sync/diff` + `sync/cleanup` API, 1시간 간격, 증분 처리(전체 재구축 아님) |
| 인증 | 전용 비관리자 계정의 API 키(`Authorization: Bearer` 헤더) |
| OCR | **보류**. 텍스트 레이어 없는 파일(손글씨 등)은 "내용 비어있음" 오류로 자동 스킵되도록 동기화 스크립트에서 정상 처리로 구분 필요. 나중에 필요시 Tesseract 등 오프라인 OCR 추가 검토(Mistral OCR 등 클라우드 OCR은 정체성상 배제) |
| 청크 크기 | 512 토큰 통일 (문서 종류별 차등은 Open WebUI가 청크 크기를 전역 설정으로만 지원해 자동화 스크립트가 복잡해지므로 보류. KB 분리 자체는 유지 — 향후 검색 범위 분리, 노트/자료 오염 방지 목적으로 전환 가능) |
| top-k | 휴대=3개, 거치=6개 |
| 검색 방식 | 휴대=Legacy Mode(자동 주입, 단일 추론) / 거치=네이티브 함수호출(정밀도 우선, 추가 추론 발생). **단, 휴대 모드를 터미널+API 방식으로 전환하면서 이 구분이 재검토 필요할 수 있음** |
| 지원 형식 | PDF, PPT/PPTX, DOC/DOCX 등 확인됨. 삼성노트 PDF 내보내기(손글씨/타이핑 혼재)는 텍스트 레이어 유무로 자동 필터링됨 |

### Docker 마운트 타이밍 검증 결과 (완료, 문제 없음)
Open WebUI는 gocryptfs 폴더를 컨테이너에 bind mount하는 구조가 아니라, 자체
named volume(`open-webui:/app/backend/data`)을 사용하고 NetworkMode가 host라
동기화 스크립트가 호스트에서 파일을 읽어 `localhost:8080` API로 전달하는 방식.
즉 컨테이너가 gocryptfs 마운트를 직접 들여다볼 필요가 없어, 처음 우려했던
"부팅 후 마운트가 컨테이너에 안 보이는" 문제 자체가 발생하지 않음. systemd 유닛도
"gocryptfs 마운트 완료 후에만 동기화 스크립트 실행"이라는 단순 조건이면 충분.

### 휴대 모드 RAG 접근 방식 변경 (진행 중)
당초 휴대 모드도 Open WebUI 화면(브라우저)으로 접속해 쓰는 걸 전제했으나, 브라우저가
OOM의 핵심 원인으로 확인되어 방향 전환:
- 휴대 모드: **브라우저 없이 터미널에서 Open WebUI 백엔드 API(`/api/chat/completions`,
  `files: [{type: "collection", id: ...}]`)를 직접 curl 호출**하는 방식으로 RAG 유지.
  매번 긴 curl 명령을 치지 않도록 `ai`/`ai-smart` 별칭과 유사한 래퍼 스크립트 필요
  (아직 미작성)
- 거치 모드: 기존처럼 Open WebUI 화면 사용

### 미해결 항목
- top-k, Legacy/네이티브 함수호출 구분이 휴대 모드의 터미널+API 전환 이후에도
  그대로 유효한지 재검토 필요
- Modelfile stop 토큰: Qwen3 8B는 검증 완료(`<|im_end|>`), Qwen3 4B는 미검증
  (Gemma 4 E2B에서 레지스트리 템플릿이 `{{ .Prompt }}` 한 줄만 있는 고장난 상태였던
  전례가 있으므로, Qwen3 4B로 전환 후에도 `ollama show --template ai` 검증 필수)
- systemd 유닛 실제 작성 (동기화 스크립트, gocryptfs 마운트 의존성)
- 언어 혼입(영어 시스템 프롬프트 + 한국어 대화) 실측 테스트 — 미실시

## 5. 오늘의 트러블슈팅 전체 타임라인 (교훈용 기록)

1. num_ctx 32768로 Gemma 4 E2B 실행 → OOM으로 프로세스 강제 종료
   (`Out of memory: Killed process ... llama-server anon-rss:~6.6GB`)
2. num_ctx를 16384로 낮춤 → 여전히 거의 동일한 메모리 사용량에서 위태로움 →
   **num_ctx는 핵심 원인이 아니었음**
3. `docker ps`로 확인한 결과 Nextcloud+Redis+MariaDB 스택이 이번 대화에서
   처음 발견됨(다른 사이드 프로젝트용, 상시 구동 중이었음) → 정지 조치
4. Nextcloud 정지 후에도 재현 시도 중 Pi5 자체가 멈췄다가 강제 재부팅됨
   (2회 반복) → 매번 파일시스템 손상 없이 정상 복구됨 확인
   (`dmesg`에 EXT4 orphan cleanup + 정상 재마운트 패턴)
5. `ollama show ai`로 Gemma 4 E2B가 실제로는 5.1B 총 파라미터 +
   vision/audio/tools/thinking capability를 가진 멀티모달 모델임을 확인
   (문서상 "E2B"는 유효 연산량 기준 명칭이지 총 파라미터가 아니었음)
6. Qwen3 8B(8.2B, 텍스트 전용)는 문제없이 실행되어, vision/audio 유무가
   메모리 문제의 핵심 변수임을 확인
7. "예전엔 Gemma 4 E2B가 멀쩡하게 돌았다"는 의문에 대해 재조사한 결과:
   - 프로젝트 기록에 이미 "num_ctx 32768에서 OOM 발생 → 16384로 낮춤"이라는
     동일 사건의 과거 이력이 있었음(이번 재현은 이 과거 기록을 확인하지 않고
     다시 32768을 시도한 것이 발단)
   - 전력 문제(모니터+키보드+마우스 추가)는 `vcgencmd get_throttled` 결과
     `0x0`으로 배제됨
   - 트레이딩 봇 2개(각 93MB)가 상시 구동 중이었음(1개인 줄 알았으나 실제로는 2개,
     단 메모리 사용량 자체는 결정적 원인 아니었음)
   - **최종 원인**: Pi5 화면에서 직접 일반 Chromium 브라우저로 Claude와 대화하며
     동시에 AI 모델을 테스트하는 작업 방식 자체가, 실제 킥오스크 배포 조건과
     다른 훨씬 무거운 환경이었음. Chromium을 완전히 종료(`pkill -9 chromium`)한
     상태에서 재현 시 Gemma 4 E2B도 정상 구동, 여유 300MB+ 유지됨
8. 다만 노트북에서 Tailscale로 원격 접속해 Open WebUI를 통해 Gemma 4 E2B를
   테스트한 결과에서도 여유 메모리가 27MB까지 떨어짐 → 브라우저 문제가
   해소되어도 여전히 위험 수준 → 모델 자체를 Qwen3 4B로 교체하는 재선정 확정

### 핵심 교훈
- **num_ctx 조정은 만능 해결책이 아니다** — 모델 자체의 고정 오버헤드(멀티모달
  capability 등)가 원인이면 컨텍스트를 아무리 줄여도 소용없음
- **파라미터 수(B)만으로 메모리 사용량을 예측하면 안 된다** — capability
  구성(vision/audio 유무)이 실제 메모리에 더 큰 영향을 줄 수 있음
- **테스트 환경이 실제 배포 환경과 다르면 결과가 왜곡된다** — Pi5 자체 화면에서
  개발용 브라우저를 띄운 채로 한 테스트는 킥오스크 실배포 조건을 대표하지 못함
- **과거에 이미 겪은 문제를 기록해두지 않으면 반복한다** — num_ctx OOM은 이번이
  최소 두 번째였음
- OOM으로 인한 Pi5 강제 재부팅은 지금까지 매번 파일시스템 손상 없이 복구됐지만,
  반복될수록 SD/eMMC 손상 누적 위험이 있으므로 재발 방지가 중요함
